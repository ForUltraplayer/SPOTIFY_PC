# 기능 검증 기록

2026년 10월 26일에 이 PC에서 확인했다. Windows 11 x64, Python 3.13.9, Spotify 1.3.6.1921, Spicetify 2.46.3, ivLyrics 7.0.16을 기준으로 한다.

| 검증 | 결과 | 범위와 한계 |
| --- | --- | --- |
| 프로젝트 이동 | 원본 파일 11 개의 SHA-256 일치 | 원본 메타데이터와 이전 문서는 Git에서 제외한 work/migration에 보존 |
| Python 회귀 검사 | 43 개 통과, 건너뛴 검사 없음 | 기존 원문 대조와 캐시, 커버 후보 및 종료 조건 검사 유지 |
| JavaScript 회귀 검사 | 19 개 통과 | 발음 연결, 알림 제거와 하단 제목 복사 범위 검사 |
| 하단 제목 우클릭 | 실제 복사 일치 | 현재 곡 제목 27 글자와 복사 결과가 정확히 일치, 단일 곡 확인 |
| 일반 실행 환경의 바로가기 | 이전 0.4.2에서 실제 시작 확인 | Spotify와 도우미를 모두 종료한 상태, 단일 PC 확인 |
| 소스 배포 초안 | 허용 목록 기반 압축과 해시 생성 | 독립 실행 설치 프로그램이 아닌 소스 초안 |

하단 재생바의 제목은 곡 링크가 아니라 앨범 링크였다. 기존 곡 메뉴의 선택 URI 판정에 걸리지 않아 복사 항목이 나오지 않았다. 현재 버전은 확인한 재생 위젯 안에서 전체 현재 제목과 일치하는 링크의 우클릭만 처리해 즉시 복사한다. 가수명과 다른 영역의 우클릭에는 개입하지 않는다. Spotify의 화면 구조가 바뀌면 이 경로의 재검증이 필요하다.

여러 곡과 Spotify 업데이트 후의 화면 회귀 검사, 다른 PC의 설치와 제거, 전체 곡의 발음 청취 검수는 완료하지 않았다. 검사 통과를 사용자 검수 완료나 정식 배포 준비 완료로 해석하지 않는다. 이전 조회 성능 수치와 실패 사례는 로컬의 이전 기록에 유지한다.

## PC 커버곡 실제 재생 후속 검증

이전에 원문부터 No lyrics found로 끝났던 히노모리 시즈쿠의 밀크 크라운 온 소네치카 커버를 Spotify에서 실제 재생했다. ivLyrics 진입 후 자연스러운 곡 전환을 사용했으며 가사 캐시 삭제나 수동 다시 불러오기는 하지 않았다. 빠른 표시 설정은 제공자 우선, 선택형 자동 발음은 켜진 상태였다.

재생 요청을 시작한 뒤 약 2.36 초에 LyricsPlus의 원문 표시 데이터 73 줄이, 약 3.18 초에 한글 발음 73 줄이 확인됐다. 기존 발음 자료는 72/73 줄이 연결됐고 1 줄은 기기 내부 자동 발음으로 보완됐다. 도우미 응답의 캐시 표시는 거짓이었으며 실제 현재 화면의 문서 요소에서도 발음 문자열 1 줄의 존재를 확인했다. 원래 가사 화면의 가상 스크롤 등으로 현재 화면에 존재하는 줄과 전체 표시 데이터 수는 다르다.

이 결과는 한 곡의 단일 실제 재생 검증이며 전체 곡의 발음 청취 검수나 평균 성능 수치가 아니다. 가사 제공 서버가 곡마다 다르므로 모든 커버곡의 성공이나 같은 속도를 보장하지 않는다. 검증 후 원래 선택했던 곡과 재생 목록 및 일시정지 상태를 복원하고 임시 디버깅 옵션을 제거한다.

## 안드로이드 후속 검증

Myspoti 기준 커밋과 한글 패치에서 Java 엔진 검사 22 개가 모두 통과했다. Kotlin·Compose 컴파일, R8 최적화, release APK 생성과 서명 검증을 통과했다. applicationId는 app.myspoti.hangul이며 versionCode는 이전 1084에서 1085로 증가했다. 로컬 설치 후보의 서명자가 이전 개인 설치용 APK와 같음을 확인했다. 원본 IPADIC 고지가 APK 안에 유지되는 것도 확인했다.

휴대폰 없이 같은 Java 엔진을 PC의 JVM에서 실행하고 공개 문서에 연결했다. 기존 PC 진단에서 얻은 원문 입력을 사용했으며 원문 파일은 Git에서 제외했다. 캐시를 쓰지 않는 새 엔진에서 메서드 호출부터 반환까지 측정한 단일 조회다.

| 곡 | 연결된 일본어 줄 | 전체 입력·출력 줄 수 | 엔진 조회 시간 | 출처 |
| --- | --- | --- | --- | --- |
| 모니터링 | 85 / 85 | 90 / 90 | 약 1.04 초 | 나무위키 원제 문서 |
| Execution Clap | 57 / 60 | 67 / 67 | 약 1.86 초 | 나무위키 처형박수 문서 |

이 시간은 휴대폰 성능 측정이 아니다. 처형박수의 남은 3 줄은 기존 발음 자료 기준으로 미일치 상태를 유지했다. 선택형 자동 발음의 단위 검사는 별도로 통과했지만 이 두 조회에서는 자동으로 만든 발음을 성공 줄 수에 합산하지 않았다.

초기 검사에서 취소된 작업이 사전 초기화에 진입해 예외를 만들던 결함을 확인했고, 네트워크 응답 직후 취소를 확인하도록 바꾼 뒤 같은 회귀 검사를 통과했다. 휴대폰 설치, 계정 로그인, 실제 제목 길게 누르기와 음악 재생 및 Spotify Connect 전환 검증은 대기한다. 휴대폰 미검증 사실을 밝힌 베타 APK는 사용자 요청에 따라 안드로이드 전용 저장소에 배포한다. 이전의 로컬 전용 방침은 이 배포 방식으로 변경했다.

## 0.5.0 설치본 후속 검증

CPython 3.13.17 내장 배포와 고정된 의존성을 설치본에 포함했다. 빌드한 내장 Python에 격리 옵션을 적용하고 PATH를 Windows System32만 남긴 상태에서 사전 변환을 통과했다. 실제 설치 후에도 같은 PATH 조건에서 시작 스크립트를 실행했고, 상태 응답의 0.5.0 도우미가 선택한 설치 폴더의 runtime/pythonw.exe로 실행되는 것을 확인했다. 기존 전역 Python이 설치된 PC이므로 이 시험은 Python 미설치 PC의 시험과 구별한다.

EXE를 한글과 공백이 들어간 전용 폴더에 설치했고 종료 코드 0과 프로그램 제거 등록 및 인용부호가 있는 제거 명령을 확인했다. 제거 완료 후 기존 Spicetify 설정, 확장, 바탕화면 바로가기, cache.json과 aliases.json이 모두 설치 전 SHA-256과 일치했다. 설치 위치 등록도 제거됐다. 설치 준비의 폴더 경계와 프로세스 식별, 원본과 적용 상태의 백업 분기 검사 8 개를 Windows PowerShell 5.1에서 통과했다.

첫 실제 설치에서는 이미 적용된 Spicetify에 다시 backup을 요청해 실패했다. 원본 .spa가 있는 상태에서만 backup apply를 사용하고 이미 적용된 상태에서는 apply를 사용하도록 고쳤다. 그 뒤 같은 경로의 설치와 제거가 성공했다. 조용한 설치의 오류 대화상자는 기본 응답으로 종료하도록 바꾸고 오류 종료 코드를 명시했다. 폴더 선택 화면의 실제 클릭 검증과 깨끗한 다른 Windows PC에서의 설치는 남아 있다.

## 0.5.1 원문 검색 후속 검증

0.5.0 설치본을 GitHub 베타로 먼저 배포하고 업로드된 EXE와 대응 소스의 해시가 로컬 검증본과 일치함을 확인한 뒤 수정했다. 발음 대조기와 개인 캐시 구조는 유지하고 원문 제공자의 추가 조회 경로를 수정했다.

제목의 feat. 괄호를 제거한 검색 후보와 공동 명의의 대표 가수 후보를 추가했다. 검색 문자열의 전각 문장부호는 보존하고 비교할 때만 유니코드를 정규화한다. 후보 검증에서 곡명, 가수, 확인 가능한 앨범과 길이를 대조하며 Live 같은 다른 버전 표기는 지우지 않는다. 응답에 신원이 없으면 같은 제공 원천의 별도 메타데이터로 확인한다. 429와 5xx 응답은 서버별로 잠시 조회를 멈추고 일시 오류로 보존한다. 추가 조회 시간은 최대 18 초이며 기본 제공자의 성공은 기다리지 않고 반환한다.

실제 설치된 ivLyrics 조회 경로에서 니고와 MORE MORE JUMP!의 기존 실패 17 곡을 대상으로 제한했다. 첫 후속 조회에서 16 곡의 원문을 확보했고 11 곡은 정리된 제목 경로로 반환됐다. 나머지 5 곡은 기존 Spotify 또는 LRCLIB 경로의 응답이었다. 남은 我らステインバスターズ！는 대표 가수명과 원래 전각 제목으로 직접 조회해 QQ 가사 61 줄을 확보했다. 이 응답으로 서버 상태가 바뀌었을 가능성을 배제하지 않으며, 최종 앱 조회에서는 기본 LyricsPlus 경로로 62 줄이 반환됐다. 따라서 후속 확인까지 합친 17 곡의 가용성을 모두 코드 수정의 인과 효과로 주장하지 않는다.

キュートなカノジョ와 きゅうくらりん은 같은 서버와 가수 및 앨범·길이 조건에서 제목의 feat.만 제거해 404에서 200으로 바뀌는 비교를 확인했다. 실제 7.0.16 파서에 저장한 응답을 재생해 각각 51 줄과 62 줄의 반환을 확인했다. 별도 캐시에서 자동 발음을 끄고 기존 발음을 대조한 결과는 50/51 줄과 61/62 줄이었다.

확장 검사 29 개와 Python 검사 43 개 및 설치 경계 검사 8 개를 통과했다. 다른 가수, 앨범, 재생 길이와 짧게 잘린 결과의 거부, 같은 원천의 신원 확인, 요청 제한 중 다른 곡의 조회와 기본 제공자의 빠른 반환 및 기존 복사와 알림 회귀를 포함한다.

실제 재생 화면 시험에서는 곡 URI 단독 지정과 소속 재생 목록 및 곡 위치 지정 두 방식 모두 목표곡으로 전환되지 않았다. 원래 일시정지된 곡의 화면에서는 한글 발음 63 줄의 데이터와 현재 화면에 있는 1 줄을 확인했으나 이 결과를 목표 커버곡의 화면 검증으로 대체하지 않는다. 원래 곡과 목록 및 일시정지 상태를 복원했다. 전체 재생 목록 검사는 재개하지 않았고 목표곡 화면과 전체 발음 청취 검수는 남아 있다.
## 0.6.0 SpotX 통합 설치 검증

2026년 10월 26일 Spotify와 SpotX를 미리 설치하지 않아도 EXE 하나로 구성하는 설치 경로를 추가했다. 실제 공식 x64 설치 파일의 SHA-256과 크기는 WinGet 입력과 일치했고 Spotify AB의 Authenticode 상태가 Valid임을 확인했다. 원본 Spotify 실행 파일은 배포물에 포함하지 않는다.

별도 APPDATA와 LOCALAPPDATA 및 Spicetify 설정을 사용한 프로필에서 한글과 공백이 들어간 빈 폴더로 최종 EXE를 설치했다. PATH는 Windows System32만 남겼다. Spotify 사전 설치가 없는 상태에서 다운로드, 검증, 파일 추출과 SpotX 및 Spicetify 및 ivLyrics 적용이 완료됐고 EXE 종료 코드와 설치 등록 버전은 각각 0과 0.6.0이었다. 같은 경로의 제거 프로그램도 종료 코드 0으로 끝났으며 시험 설치 폴더가 제거됐다. 시험 전에 보존한 실제 설치 등록과 메뉴 및 바탕화면 바로가기를 복원했다. 바로가기의 SHA-256도 이전 값과 일치했다. 이 시험은 전역 Python이 설치된 현재 PC 안의 별도 프로필 시험이며 다른 물리 PC에서의 검증과 구별한다.

기존 실제 설치의 업데이트도 EXE 종료 코드 0과 버전 0.6.0 등록을 확인했다. 새 경로의 Spotify.exe가 실행된 것을 프로세스 경로로 확인했다. 기존 로그인 상태를 사용해 ivLyrics 화면을 열었고 요네즈 켄시의 さよーならまたいつか！에서 일본어 원문과 한글 발음이 함께 표시됐다. 화면은 Spotify Connect의 재생 상태를 표시했으므로 이 결과만으로 로컬 오디오 출력이나 광고 차단을 검증했다고 주장하지 않는다. 새 실행 경로의 Windows 네트워크 허용 요청은 사용자가 직접 처리했다.

설치 직후 가사 화면을 열기 전에 기존 Spotify 실행 파일과 DLL 및 xpui.js, 공유 Spicetify 설정과 확장, 발음 cache.json과 aliases.json의 총 7 개 파일을 비교했다. 모두 설치 전 SHA-256과 일치했다. 이후 가사 요청에 따른 정상 캐시 갱신은 설치로 인한 변경과 구별한다.

Python 43 개, JavaScript 29 개와 기존 설치 보호 검사 8 개 및 통합 설치 검사 12 개가 통과했다. 통합 검사는 폴더 경계, 잘못된 크기와 해시 거부, 실제 서명 파일 입력 및 분리 패치 코드의 외부 작업 제외를 확인한다. 잘못된 Spicetify 백업 버전과 경로를 주입한 재적용에서는 오류를 감지했고 해당 시도의 설정 폴더와 Spotify Apps 폴더가 모두 직전 해시로 복원됐다. 먼저 시험한 ivLyrics 파일 누락은 설치 코드가 다시 준비해 정상 완료했으므로 실패 복구 검증으로 계산하지 않았다.

처음 실제 EXE 시도는 종료 코드 1이었으나 당시 오류 로그가 부족해 단일 원인을 확정하지 못했다. 별도 빈 환경의 EXE에서는 Get-FileHash를 찾지 못하는 오류와 Microsoft.PowerShell.Security 모듈 로드 실패를 재현했다. NSIS에서 네이티브 64 비트 PowerShell을 명시하고, 해당 인터프리터의 내장 모듈 경로 및 보안 모듈을 직접 사용하도록 바꿨다. SHA-256은 시스템 암호화 기능으로 직접 계산하도록 바꿨다. 이후 같은 제한 PATH 조건의 새 EXE 설치와 제거가 통과했다. 도우미 종료 대기와 설치 단계 및 오류 원문 기록도 추가했다.

Windows 10과 ARM64, Store판 공존, 다른 보안 제품 및 다른 물리 PC의 검증은 남아 있다. 실제 광고 수신 전후의 통제 재생과 전체 재생 목록 재검사는 수행하지 않았다. 사용자가 중단한 전체 검사는 재개하지 않았다.

## 0.6.1 발음 재조회와 자동 업데이트

2026년 10월 26일에 발음 조회의 재시도 범위를 확장했다. 최초 조회 이후 2 초 간격으로 최대 3 회 추가 조회하며 전체 요청 시간은 최대 60 초다. 성공 결과는 즉시 반환하고 곡 변경 시 진행 중인 HTTP 요청과 대기 타이머를 중단한다. 다음 곡의 미리 조회는 반복 검색하지 않는다. 알림 팝업은 추가하지 않는다.

도우미의 실패 캐시가 실제 재검색을 막지 않도록 현재 곡의 재시도에 한해서 실패 캐시를 우회한다. 같은 실패가 계속되면 원문과 발음 및 지정 출처로 구분한 요청마다 추가 검색을 3 회로 제한한다. 성공 캐시와 기존 발음 판정 기준은 유지한다. 서버가 혼잡한 경우 추가 검색 횟수를 사용하지 않으며, 프런트엔드의 전체 횟수와 시간 상한은 유지한다.

Python 검사 46 개와 JavaScript 검사 37 개를 통과했다. 새로운 사례는 실패 캐시 우회와 복구, 화면 재진입 시 무한 재조회 방지, 정상 응답 즉시 반환, 다음 곡 미리 조회의 제한, 곡 변경 취소와 전체 시간 상한을 확인한다. 실제 확장과 실제 Python HTTP 처리기를 연결한 격리 시험에서는 첫 출처 응답을 의도적으로 실패시킨 뒤 실제 2 초 대기를 거쳐 두 번째 요청으로 5 줄의 발음을 받았다. 출처 내용은 합성 자료이며 실사이트의 간헐 오류를 재현한 시험은 아니다. 이미 정상 결과가 전달됐는데 화면만 비는 현상을 모두 해결했다고 주장하지 않는다.

GitHub 업데이트 검사는 지정 저장소의 정확한 Setup.exe 주소와 SHA-256 및 크기와 파일 버전만 허용한다. 외부 저장소, 초안과 동일 버전, 해시 없는 자산, 손상된 파일, Spotify 실행 중 적용 차단과 오프라인 실행 지속 등을 13 개 검사로 확인했다. 이 검사의 설치 프로세스는 모형이며 실제 OS 설치 검증과 구별한다. 별도 폴더에서 공개 GitHub API에 연결해 현재 버전보다 높은 배포가 없는 경우의 응답과 상태 저장도 확인했다. 설치 보호 검사와 실제 서명 입력 검사는 별도로 유지한다.

기존 사용자는 약 90 KB의 Update.exe로 처음 한 번 갱신할 수 있다. 이 실행기는 최신 Setup.exe 약 65 MB를 내려받아 기존 폴더에 적용한다. 차등 패치는 아니며 기존 통합 Spotify는 다시 받지 않는다. 자동 업데이트 프로세스의 시작 조건과 수명 및 상태 파일은 운영 안내에 기록한다.

배포 후 공개 GitHub 자산을 실제로 내려받아 0.6.0에서 0.6.1로 갱신했다. Spotify 실행 중에는 적용 종료 코드 20으로 보류됐고, 확인한 통합 Spotify를 종료한 뒤 적용과 시작 스크립트가 각각 종료 코드 0으로 완료됐다. 설치 기록과 실행 중인 도우미 버전 모두 0.6.1이었다. 업데이트 직후 cache.json과 aliases.json 두 파일의 SHA-256은 이전 값과 일치했다. 배포한 Update.exe 실행기도 이미 최신 버전인 상태에서 종료 코드 0을 확인했다. 따라서 실제 버전 전환은 업데이트 스크립트와 실제 배포 설치본으로 검증했으며, 작은 실행기는 최신 상태 검사 경로를 별도로 확인했다.

## 0.6.2 구성 요소 관리와 ivLyrics 교체

2026년 10월 26일에 구성 요소의 버전과 다운로드 해시를 components.json으로 통합했다. 기존 다운로드 영수증은 빌드 기준에서 제외하고 설치, SpotX 버전 확인과 배포 빌드가 같은 목록을 읽는다. Spicetify 2.46.4를 공개 GitHub에서 후보로 내려받아 SHA-256과 크기 및 실행 파일 버전을 확인하고 자동 검사 후 개발 목록에 반영했다.

Python 발음 검사 46 개, 구성 요소 검사 6 개, JavaScript 검사 37 개, 기존 설치 보호 검사 8 개, 통합 설치 검사 11 개, 자동 업데이트 검사 13 개와 ivLyrics 교체 검사 11 개로 합계 132 개가 통과했다. 실제 ivLyrics 7.0.16 소스의 구문, 캐시 연결 함수와 공개된 LyricsPlus 파서에 합성 가사 두 줄을 입력하는 검사도 통과했다. 검사 보고서는 목록과 검사한 소스 해시에 연결하며 파일 변경 후 같은 보고서를 재사용해 빌드하거나 후보를 반영하지 못하도록 했다.

별도 work 하위의 한글 및 공백 경로에서 공식 Spotify 파일 추출, 실제 SpotX 적용과 Spicetify 2.46.4 적용을 완료했다. 기존 ivLyrics의 index.js를 바꾸고 이전 버전에만 있는 합성 파일을 추가한 뒤 실제 설치 훅을 다시 실행했다. 새 index.js가 동봉 파일과 일치하고 오래된 파일이 사라졌으며 이전 코드 전체가 backup에 보존됐다. 별도 테마 설정과 합성 발음 캐시의 해시는 유지됐다.

추가로 기존 코드와 Spicetify 백업 버전을 의도적으로 변경해 실제 -n apply 실패를 발생시켰다. 설치 훅은 오류를 반환했고 ivLyrics, spicetify-config 전체 및 Spotify Apps 전체 파일의 경로와 SHA-256 목록이 실패 직전과 일치했다. 오류 원문은 격리 로그에 남겼다. 이 검사는 실행 중인 개인 설치본을 바꾸지 않고 진행했으며 새 조합의 실제 로그인과 가사 화면 및 광고 동작을 확인한 검사는 아니다.

0.6.2 Setup.exe와 Update.exe 빌드는 완료했다. README의 현재 공개 버전 표시는 0.6.1로 유지하고 새 유지 관리 절차를 개발자 항목에 추가했다. 새 CI의 실제 GitHub 실행은 별도로 확인한다.
