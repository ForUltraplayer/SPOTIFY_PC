## 시작과 수명

바탕화면 바로가기는 도우미를 준비한 뒤 Spotify를 실행한다. 일반 Spotify 바로가기는 도우미를 시작하지 않는다. 같은 한글 가사 바로가기를 여러 번 실행해도 정상 응답하는 기존 도우미를 재사용한다. EXE 설치본은 내장 Python을 사용한다. 개발용 명시 환경 변수 IVLYRICS_HANGUL_PYTHON을 지정한 경우에는 그 경로가 우선한다.

버전 0.6.0부터 한글 가사 바로가기는 설치 폴더 안의 통합 Spotify를 연다. 기존 Spotify가 실행 중이면 설치 기록과 기본 경로로 확인한 이전 클라이언트만 종료한다. 두 클라이언트의 사용자 데이터는 Spotify 기본 프로필을 사용하므로 동시에 실행하지 않는다. 기존 Spotify의 파일과 부팅 자동 시작 설정은 바꾸지 않는다. 기존 자동 시작으로 일반 Spotify가 열렸다면 한글 가사 바로가기를 다시 실행한다.

도우미는 같은 PC의 루프백 주소에서만 요청을 받는다. 사전을 초기화한 뒤 메모리에 유지하며 GPU와 음성 장치는 사용하지 않는다. 별도 프로세스는 Spotify 안의 직접 요청과 기본 프록시 경로에서 나무위키 본문을 읽지 못했던 검증 결과를 바탕으로 추가했다. 다른 외부 프록시로 교체하는 대안은 시험하지 않았다.

서비스, 부팅 자동 시작과 실패 후 재시작은 등록하지 않는다. Spotify가 사라진 뒤 약 30~35 초 후 종료하며 시작 시 Spotify를 기다리는 유예 시간은 120 초다. 중지 스크립트는 상태 응답의 프로세스 번호와 설치 경로가 일치할 때만 도우미를 종료한다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "선택한 설치폴더\stop.ps1"
```

프로그램 제거는 Windows 설치된 앱에서 진행한다. 개인 캐시를 삭제할 필요는 없다. 통합 Spotify는 자동 업데이트를 차단하며 버전 교체는 새 통합 설치본으로 진행한다. 검증용 디버깅 포트는 상시 사용하지 않으며 진단 후 해당 옵션 없이 Spotify를 다시 실행한다.

이번 작업의 개인 실행 이력, 임시 검사 도우미와 프로세스 번호는 Git에서 제외한 work/runtime/RUNNING.md에 기록한다. 재생 목록 검사는 별도 포트와 별도 캐시를 사용하므로 많은 곡을 검사해도 사용 중인 500 곡 캐시를 밀어내지 않는다. 임시 검사 프로세스는 작업 후 종료한다.

## GitHub 자동 업데이트

0.6.1부터 시작 스크립트는 Spotify를 열기 전에 내려받은 업데이트가 있는지 확인한다. Spotify 프로세스가 열려 있으면 적용을 미룬다. Spotify 실행 후 별도 Windows PowerShell 프로세스가 프로젝트 GitHub 릴리스를 확인하고 새 Setup.exe를 내려받은 뒤 종료한다. 확인 간격은 최소 8 시간이며 실행 중에 주기적으로 계속 감시하는 구조는 아니다. 0.7.4부터 간격을 4 시간으로 줄였다. 확인은 바로가기로 실행할 때 GitHub API를 한 번 조회하는 것이라 실행 중 자원은 쓰지 않는다. 이미 설치된 0.7.3 이하는 새 버전으로 업데이트되기 전까지 8 시간 간격을 쓴다.

0.7.4부터 시작 때의 백그라운드 확인은 새 버전을 조용히 내려받지 않고 확인창을 띄운다(`update-ui.ps1`, WinForms, 맨 위 표시). 「아니요」는 `declined`를 기록하고 다음 확인 간격 뒤에 다시 묻는다. 「예」는 진행률 창에서 내려받고 크기, SHA-256, 파일 버전을 확인한 뒤 Spotify 프로세스에 닫기 요청을 보낸다. 닫히지 않은 프로세스만 강제로 종료하고 `Setup.exe /S`로 설치한 다음 바로가기와 같은 명령으로 다시 실행한다. 설치가 실패하면 설치 프로그램의 복원 뒤 이전 버전을 다시 실행한다. 이미 내려받아 둔 `pending.json`과 `Update.exe`(`-Interactive`)는 기존처럼 창 없이 적용한다. 0.7.3 이하 설치본은 0.7.4를 기존 방식(조용히 내려받아 다음 실행 때 적용)으로 받는다.

Spotify 프로필 메뉴의 「Spotify 한글 가사 (버전) · 업데이트 확인」은 도우미의 `POST /update/check`를 부른다. 도우미는 `auto-update.ps1 -Mode Check -IgnoreInterval -Manual`을 창 없는 콘솔의 PowerShell로 분리 실행하고, 결과(새 버전 확인창, 최신 버전 안내, 오류)는 업데이터 창이 보여 준다. 확인이 겹치면 업데이트 잠금으로 두 번째 창을 막는다. 바로가기처럼 `conhost.exe --headless`를 쓰면 도우미가 넘기는 빈 표준 입력을 콘솔 호스트가 입력 종료로 읽어 업데이터가 곧바로 끝났다. 2026-10-28 이 PC에서 확인했고, `CREATE_NO_WINDOW`로 실행하면 창이 정상으로 뜨고 터미널 창도 생기지 않았다.

데스크톱 가사창 자동 실행도 0.7.4에서 다시 넣었다. 이번에는 시작 스크립트가 아니라 ivLyrics의 「데스크탑 오버레이 사용」이 켜져 있고 가사창이 연결되지 않았을 때만 실행한다. ivLyrics 가사 화면이 열릴 때와 YouTube 곡의 「가사 열기」 때 도우미의 `POST /overlay/launch`를 부르며, 같은 요청은 30 초에 한 번으로 제한한다. 도우미는 `%LOCALAPPDATA%\lyrics-plus-overlay\lyrics-plus-overlay.exe` 고정 경로만 실행하고, 같은 이름의 프로세스가 있으면 실행하지 않는다. 프로세스 확인은 포트 15000 연결이 아니라 프로세스 목록으로 한다. 시작 중인 가사창은 아직 포트를 열지 않았고, 일부 PC에서 리스너 목록이 잘못 보고되기 때문이다. 원본 ivLyrics 7.0.16의 `openOverlayApp()`은 정의만 있고 호출되지 않으며 등록되지 않은 `ivLyrics://` 주소를 쓴다. Spotify 페이지에서 `ivlyrics-overlay://`를 `window.open`, 링크 클릭, 숨은 iframe으로 여는 방법은 2026-10-28 이 PC에서 모두 실행되지 않아 도우미가 실행하는 방식을 택했다. 실패한 설치의 동일 버전 자동 적용은 중단하며 수동 Update.exe로 다시 시도할 수 있다.

## 0.7.5의 YouTube 음량

0.7.4까지 YouTube 음원 모드는 같은 볼륨에서 Spotify 곡과 영상 모드보다 크게 들렸다. 원인은 두 가지였다. 첫째, YouTube 플레이어는 시청 페이지의 `playerConfig.audioConfig.loudnessDb`(형식별 값이 있으면 그 값)만큼 큰 곡을 줄여 기준 음량(−14 LKFS)에 맞추고 작은 곡은 키우지 않는데, 음원 모드는 원본 Opus를 그대로 재생했다. 확인한 곡들은 기준보다 4.6~9 dB 컸다. 0.7.5부터 도우미가 yt-dlp 조회와 함께 시청 페이지를 읽어 `volume_gain`(`10^(-loudnessDb/20)`, 최대 1)을 돌려주고, 음원 모드는 이 비율을 곱한다. 값을 읽지 못하면 비율은 1이다.

둘째, 슬라이더 곡선이 달랐다. 2026-10-28 이 PC에서 WASAPI 루프백으로 같은 구간을 반복 측정한 결과, Spotify 곡은 슬라이더 10 %마다 약 4 dB씩 줄었다(50 %에서 약 −19~−21 dB, 10 %에서 약 −35~−37 dB). 반면 오디오 요소와 YouTube 내장 플레이어는 50 %에서 −5 dB 정도만 줄었다. 그래서 중간 볼륨에서 YouTube가 10 dB 이상 컸다. Spotify 자체 볼륨은 YouTube 재생 음량에 영향을 주지 않았다. `youtube-links.js`는 측정한 세 곡선(`SPOTIFY_DB`, `AUDIO_DB`, `VIDEO_DB`)으로 슬라이더 값을 Spotify와 같은 크기가 나는 오디오 요소 볼륨과 플레이어 볼륨으로 바꾼다. 슬라이더와 상태값은 사용자가 고른 값을 그대로 유지한다. 볼륨 값도 하나로 합쳤다. YouTube 항목을 시작할 때 Spotify의 현재 볼륨을 가져오고, YouTube 재생 중 바꾼 볼륨은 Spotify 볼륨에도 기록한다. 0.7.4까지는 YouTube 볼륨이 25에서 따로 시작해 곡이 바뀔 때마다 슬라이더가 움직였다. 바꾼 뒤 다시 측정했을 때 음원 모드는 전 구간에서, 영상 모드는 50 % 이상에서 Spotify 곡과 3 dB 안쪽이었다. 내장 플레이어는 정수 1 % 아래로 내려가지 않아 영상 모드는 약 −24 dB(슬라이더 약 35 %)에서 더 작아지지 않는다. 100 %에서 음원 모드와 영상 모드는 같은 구간에서 0.3 dB 안쪽이었다.

측정은 이 PC의 출력 장치 하나에서만 했다. 다른 PC나 다른 출력 장치에서 곡선이 같은지는 확인하지 않았다. Spotify의 음량 평준화 설정을 바꾸면 Spotify 곡 쪽 크기도 달라진다.

## 0.7.6의 저장소 이름 변경 대비

0.7.5까지 업데이터는 `repos/ForUltraplayer/SPOTIFY_PC/releases`로 릴리스를 조회하고, 자산 주소가 `https://github.com/ForUltraplayer/SPOTIFY_PC/releases/download/...`와 정확히 같을 때만 받았다. 저장소 이름을 바꾸면 GitHub가 돌려주는 자산 주소에 새 이름이 들어가므로 0.7.5 이하는 새 버전을 찾지 못한다. 0.7.6부터는 이름이 바뀌어도 그대로인 저장소 번호로 조회한다(`repositories/1433444843/releases`). 자산 주소는 소유자가 `ForUltraplayer`이고 태그와 파일 이름이 맞으면 저장소 이름과 관계없이 받으며, 내려받을 때도 GitHub가 돌려준 주소를 그대로 쓴다. 다른 소유자의 같은 이름 저장소와 다른 파일 이름은 거부한다. 저장소 이름 변경은 0.7.6이 기존 설치본에 충분히 퍼진 뒤에 한다.

## 0.7.7의 설치·업데이트 창 언어와 설치 폴더 검사

0.7.6까지 설치 프로그램은 NSIS 언어를 한국어, 영어 순으로 등록했다. NSIS는 Windows 표시 언어와 맞는 언어가 없으면 처음 등록한 언어를 쓰므로 스페인어, 일본어, 중국어 Windows에서도 한국어 화면이 나왔다. 직접 넣은 오류 창 문구는 영어 Windows에서도 한국어였다. 2026-10-29 스페인어 사용자가 한국어 설치 실패 창을 그대로 복사해 이슈로 올린 일이 계기다. 0.7.7부터 Setup.exe와 Update.exe는 영어를 먼저 등록하고, 직접 넣은 문구마다 한국어와 영어를 둔다. 업데이트 확인 창, 진행 창과 업데이트 오류 문구는 Windows 표시 언어가 한국어면 한국어, 아니면 영어로 표시한다. 시험에서는 `SPOTIFYHANGUL_LANGUAGE`(`ko` 또는 `en`)로 고정한다. 시작 스크립트의 오류 창과 Spotify 안의 화면은 아직 한국어만 지원한다.

설치 폴더는 폴더 선택 화면에서 다음으로 넘어갈 때와 창 없는 설치(`/S /D=`)의 시작 때 검사한다. 드라이브 최상위, 사용자 폴더, AppData, LocalAppData, Program Files, Windows 폴더 자체와 설치 표식(`install-marker.json`)이 없는 비어 있지 않은 폴더는 이유와 예시 경로를 보여 주고 거부한다. 같은 조건은 `payload-transaction.ps1`에도 있지만, 이전에는 설치 파일을 풀고 적용을 시작한 뒤에야 같은 실패 창이 떴다. 2026-10-29 이 PC에서 창 없는 설치로 다른 파일이 든 폴더와 `%LOCALAPPDATA%`가 1 초 안에 거부되고 폴더와 복구 기록이 바뀌지 않는 것, 기존 설치 폴더 덮어쓰기는 정상으로 끝나는 것을 확인했다. 폴더 선택 화면의 안내 창과 영어 화면은 직접 보지 않았다.

0.7.7은 한국어 사용자에게 필요 없는 변경이라 GitHub 시험판(prerelease)으로 게시한다. 0.7.0 이후 업데이터는 시험판을 건너뛰지만 0.6.x 업데이터는 시험판 표시를 확인하지 않으므로, 0.6.x 설치본은 0.7.7로 올라갈 수 있다.

GitHub 공개 API와 이 소유자의 릴리스 자산 주소만 사용하고 파일 크기 및 GitHub 자산 SHA-256과 설치 파일의 버전을 검사한다. 이는 코드 서명이나 GitHub 계정 침해 방어를 대신하지 않는다. 다운로드는 최대 180 초, 설치 완료 대기는 최대 600 초로 제한한다. 상태는 업데이트 저장 폴더의 state.json과 pending.json에 기록한다. 다운로드와 적용에는 각각 잠금을 사용하며 설치 중인 경우 두 번째 실행이 겹치지 않도록 한다.

별도 서비스를 등록하거나 Windows 자동 시작을 추가하지 않는다. 기존 시작 스크립트와 검증한 통합 설치본을 재사용하는 방식을 선택했다. 상주 서비스와 차등 파일 패치는 시험하지 않았다. Update.exe는 작은 다운로드 실행기이며 약 65 MB의 통합 설치본을 추가로 받는다. 자동 업데이트로 기존 통합 Spotify를 재사용하는 경우 Spotify 본체를 다시 받지 않는다. 업데이트 상태를 포함한 개인 데이터는 프로그램 제거 후에도 남는다.


## 0.6.3 전처리 상태 분리와 오류 안내

0.6.2는 업데이트 실패로 비공개 초안으로 전환했고 수정한 0.6.3을 공개 베타로 배포한다. 이전에는 SPICETIFY_CONFIG만 지정해 실제 Backup과 Extracted가 APPDATA의 공유 폴더에 남는 결함이 있었다. Spicetify 원본의 GetStateFolder 구현에서 이 동작을 확인했다. 0.6.3은 설치 훅의 자식 프로세스에만 SPICETIFY_STATE를 지정하고 설치 폴더 안의 별도 상태를 사용한다. 전역 환경 변수와 자동 시작은 등록하지 않는다.

처음 전환할 때는 기존 공유 백업이 해당 통합 클라이언트의 자료인지 확정할 수 없어 그대로 복사하지 않는다. 검증한 공식 Spotify 설치 파일 약 150 MB를 내려받아 SpotX가 적용된 UI 원본을 다시 준비한다. 이후에는 자체 백업을 사용한다. 공유 백업과 기존 Spotify 실행 파일을 변경하지 않으며 설정, 앱 코드와 Spotify Apps 및 자체 전처리를 이번 시도 직전 상태로 복원할 수 있게 보존한다.

Spicetify의 전처리 버전과 새 CLI 버전이 다르면 restore backup apply를 사용하고, 같으면 기존 전처리를 재사용한다. 설치 실패, Spotify 실행, 다른 업데이트 작업과 시간 초과는 각각 다른 오류로 안내한다. 팝업에는 실제 원인과 필요한 로그 위치를 표시한다. 재부팅으로 이전 설치 프로세스가 사라진 경우 수동 재시도는 검증 후 진행할 수 있고 자동 재시도는 중단 상태를 유지한다. 상태 JSON은 BOM 유무와 관계없이 UTF-8로 읽는다.

비공개 검증본은 공개 릴리스 목록에 나오지 않으므로 Update.exe로 받을 수 없다. 초안의 Setup.exe를 기존 설치 폴더에 덮어 설치한다. 공개 목록에서 유효한 후보를 찾지 못한 경우 남은 이전 대기 파일을 철회 상태로 격리한다. 내려받은 파일과 대기 메타데이터는 조사용으로 보존한다. Update.exe는 자신의 요청 버전보다 낮은 공개 후보로 대신 설치하거나 설치되지 않은 비공개 버전을 최신 상태로 안내하지 않는다.

## 0.7.0 로컬 후보의 설치 복원과 오버레이

설치 프로그램은 새 파일을 임시 폴더에 먼저 풀고 해시를 검사한다. 기존 설치가 있으면 실행 중인 해당 설치의 Spotify와 도우미 및 내장 오버레이를 종료한 뒤 설치 폴더 전체를 보존한다. 코드와 내장 실행 도구 및 통합 처리가 실패하거나 설치 등록에 실패하면 이전 파일과 등록 및 바로가기를 복원한다. 설치 도중 전원이 꺼진 경우에는 같은 Setup.exe를 다시 실행해 복구한다. 성공한 설치를 사용자가 임의의 구버전으로 되돌리는 기능과는 구분한다.

복구 기록은 설치 폴더 옆의 `.설치폴더명-update-경로해시` 폴더에 둔다. 이전 파일은 `previous`, 실패한 시도의 자료는 `failed`, 상태는 `journal.json`으로 남긴다. 다음 설치 시 완료된 기록 한 세대를 정리하고 새 기록을 만든다. 제거 프로그램은 소유권을 확인한 완료 기록도 함께 정리한다. 설치 파일의 임시 압축 해제 공간과 전체 이전 폴더를 복사할 공간이 추가로 필요하다.

복구 전에는 보존한 파일 목록과 해시를 대조한다. 백업이 없거나 손상된 경우에는 복구 완료로 표시하지 않고 진단을 위해 중단한다. 진단 로그를 저장하지 못한 경우에도 파일 복구 시도는 유지한다.

기존 업데이터나 터미널이 설치 폴더를 작업 폴더로 사용해 폴더 이동이 막히면 파일을 원래 자리에 복원한다. 이 경우 원본 백업을 유지하며 복구가 중단돼도 재시도한다. `failed`에는 변경되거나 새로 추가된 파일만 진단용으로 보관하고 일부 자료가 남지 않을 수 있다. 진단 복사 실패는 핵심 파일 복구를 막지 않으며, 전체 파일의 해시가 이전 상태와 일치한 뒤 설치 등록과 바로가기를 복원한다.

기존 Tauri 데스크톱 오버레이는 설치 폴더의 `desktop-overlay`에 포함한다. 별도의 WPF 시제품으로 교체하지 않는다. 기본 바로가기는 내장 파일의 해시와 실행 경로를 확인하고 오버레이를 시작한다. 기존 별도 설치본이 같은 파일이면 재사용하며, 다른 파일이 실행 중이면 먼저 종료하도록 안내한다. 기존 설정 식별자와 창 위치 저장 방식을 유지한다. 새 부팅 자동 시작이나 서비스를 등록하지 않는다. 오버레이는 기존처럼 트레이에서 종료할 때까지 남을 수 있다.

창 이동은 기존 동작 탭에서 잠금을 해제한 뒤 가사창의 빈 영역을 드래그한다. 레이아웃 탭에 중복 잠금 해제나 창 위치 및 높이 조절 버튼을 추가하지 않는다. 제목과 원문 및 발음 사이 간격은 기존 레이아웃의 간격 설정을 사용한다.

발음과 재생 버튼이 겹치지 않도록 버튼은 가사 다음의 별도 영역을 사용한다. 레이아웃 탭의 재생 버튼 섹션에서 세로 위치 슬라이더로 조절한다. 기존 간격 설정을 그대로 사용하며 기본 12 논리 픽셀이고 범위는 0~48이다. 값이 커지면 버튼이 가사 아래로 내려간다. 슬라이더를 드래그하거나 그 위에서 휠을 굴려 조절하며 휠을 아래로 내리면 2 논리 픽셀씩 간격이 늘어난다. 창 크기와 위치 및 잠금 설정은 바꾸지 않는다. 다른 가사 영역의 휠은 기존 스크롤 동작을 유지한다. 마우스 오버 때만 버튼을 표시하는 경우에도 공간을 유지해 가사가 위아래로 움직이지 않게 한다. 버튼을 완전히 숨기면 가사 영역을 다시 넓게 쓴다. 창 높이가 부족하면 가사 영역 안에서 현재 발음 부분을 우선 표시하고 스크롤한다. 작은 창에서는 버튼을 더 내리는 대신 가사 영역이 줄어들 수 있으며 모든 줄을 동시에 보여 주지는 않는다.

이 후보는 원본 오버레이의 배포 라이선스가 확인되지 않은 로컬 검증본이다. 원본 소스와 로컬 수정 및 바이너리 해시를 설치본에 보존하며, 공개 가능 여부를 확정한 것으로 표시하지 않는다. 원본 오버레이의 자체 업데이트를 설치하면 이 묶음의 수정이 덮일 수 있다. 원본 Tauri 앱에 필요한 Windows WebView2 Runtime도 필요하다. 공개 릴리스가 없는 동안은 이 후보의 Setup.exe를 기존 폴더에 직접 설치한다.

Windows의 설정 창 생성은 짧게 실행되는 전용 작업 스레드에서 처리한다. 두 번째 실행과 트레이 메뉴 및 첫 실행 안내가 같은 경로를 사용하며 중복 생성 요청은 합친다. 사용 중인 Tauri SDK가 Windows 이벤트 처리 중 동기 WebView 생성의 교착을 명시하고 있어 해당 경로를 분리했다. 별도 상주 프로세스나 서비스는 추가하지 않는다.

## 0.7.2의 오버레이 분리

0.7.2부터 설치본은 데스크톱 오버레이를 포함하지 않는다. 시작 스크립트는 오버레이가 이미 실행 중이면 그대로 재사용하고, 아니면 `%LOCALAPPDATA%\lyrics-plus-overlay\lyrics-plus-overlay.exe`가 있을 때만 시작한다. 파일이 없으면 아무것도 하지 않는다. 오버레이 시작에 실패해도 Spotify 실행은 계속하며 오류는 설치 폴더의 `start-error.txt`에 남긴다. 0.7.0에서 자동 업데이트한 직후의 첫 실행은 메모리에 남은 0.7.0 시작 스크립트가 옛 함수 이름을 호출하므로, 같은 이름의 호환 함수가 오류를 삼키고 새 동작으로 넘긴다. 업데이트 때 제거하는 것은 설치 폴더 안의 0.7.0 사본뿐이며 사용자가 따로 둔 오버레이는 종료하거나 지우지 않는다. 설치 완료 화면에서 포크 릴리스 링크를 안내한다.

0.7.3에서는 위의 자동 시작을 없앴다. 원래 ivLyrics처럼 사용자가 ivLyrics 설정의 데스크탑 오버레이 사용을 켜면 ivLyrics가 오버레이를 연다. 시작 스크립트는 오버레이를 띄우지도 기다리지도 않으며, 0.7.0 호환 함수도 아무것도 시작하지 않는다. 이 변경과 함께 시작 순서를 바꿔 도우미를 확인한 직후 Spotify를 실행하고, 내려받아 둔 업데이트가 있을 때만 업데이트 적용 단계를 실행한다. 이 PC 측정 기준으로 콜드 스타트는 7.1 초였고, 그중 약 4 초가 오버레이 대기, 약 1 초가 대기 업데이트 없는 업데이트 적용 단계였다.

바로가기, 설치 완료 화면의 실행, 백그라운드 업데이트 확인은 `conhost.exe --headless`로 PowerShell을 띄운다. Windows 11의 기본 터미널이 Windows Terminal이면 `-WindowStyle Hidden`을 줘도 창이 나타나는 것을 이 PC에서 확인했고, headless 콘솔 호스트에서는 창이 생기지 않았다. 바로가기 인수에는 계속 `start.ps1` 경로가 들어 있어 기존 바로가기 판별 코드는 그대로 동작한다. Windows 10 1809 이전 빌드는 `--headless`를 지원하지 않으며 검증하지 않았다.

도우미는 0.7.3부터 HTTP/1.1 연결 유지로 응답한다. 테스트 PC에서 AdGuard for Windows의 네트워크 드라이버(`adgnetworkwfpdrv`, `adgnetworksockdrv`)가 켜져 있으면, 서버가 먼저 연결을 닫는 HTTP/1.0 루프백 응답이 리셋되거나 64 KiB에서 잘렸다. 이것이 "Failed to fetch", 플레이어 화면의 ERR_CONNECTION_RESET, YouTube 모듈과 「지금 재생 중」 스타일 로드 실패의 원인이었다. AdGuard를 끄면 280회 요청이 모두 성공했고, 켠 채로 연결 유지 방식을 쓰면 40회가 모두 성공했다. 연결 유지에서는 응답마다 길이를 보내고, 본문을 읽기 전에 거절한 POST는 남은 본문을 비운 뒤 응답한다. 비우지 않으면 다음 요청이 그 본문을 요청 줄로 읽는다. 쉬는 연결은 330 초 뒤 닫아 스레드를 돌려준다. Chromium의 유휴 연결 보관 시간(5 분)보다 길게 잡아 Spotify와 오버레이가 먼저 닫게 한다. 다른 백신의 네트워크 보호 기능이 같은 방식으로 동작하는지는 확인하지 않았다.

업데이트 복구 기록 정리가 실패해도 제거를 막지 않는다. 제거 프로그램은 기록 폴더를 그대로 둔 채 계속할지 묻고, 무인 제거에서는 기존처럼 중단한다.

설치 바로가기의 작업 폴더는 설치 위치로 고정한다. Spotify를 실행할 때는 해당 EXE가 있는 폴더를 작업 폴더로 지정해 바로가기나 PowerShell을 실행한 위치에 의존하지 않게 한다. 시작 스크립트와 업데이터는 설치를 기다리는 동안 자신의 작업 폴더를 임시 폴더로 옮겨 설치 폴더를 점유하지 않게 한다. 제거 프로그램도 설치 폴더 밖으로 작업 폴더를 바꾼 뒤 파일을 정리한다.
